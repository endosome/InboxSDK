# InboxSDK architecture analysis (for the Calendar SDK fork)

Status: **Phase 0 — repo analysis complete; derived from reading source at
commit `94d8cee7` (v2.2.27).** Everything here is verified against files in this
repo unless tagged `[UNVERIFIED]`.

Classification legend: `KEEP` · `KEEP+MOD` (keep with modifications) · `GENERIC`
(refactor into generic infrastructure) · `REPLACE` · `DELETE` · `EXPERIMENT`
(unknown, needs experiment).

## 1. Layers and runtime topology

```
Extension content script (ISOLATED world)                     Page (MAIN world)
┌────────────────────────────────────────────┐               ┌──────────────────────────────┐
│ src/inboxsdk-js/inboxsdk.ts  (loader)      │               │ src/injected-js/main.ts      │
│   load() → PlatformImplementationLoader    │               │  (built to pageWorld.js)     │
│ src/platform-implementation-js/            │  DOM events   │  setup-gmail-interceptor     │
│   main.ts  → __InboxSDKImpLoader.load()    │◄─────────────►│  setup-gmonkey-handler       │
│   platform-implementation.ts               │  + attributes │  setup-data-exposer          │
│   ├─ namespaces/*  (public API)            │  on <head>/   │  xhr-helper, event-reemitter │
│   ├─ views/*       (public view objects)   │  elements     │  thread-identifier/*         │
│   ├─ lib/Membrane  (driver → view)         │               └──────────────────────────────┘
│   ├─ driver-interfaces/*                   │
│   └─ dom-driver/gmail/*  (GmailDriver …)   │
└────────────────────────────────────────────┘
  background.js (packages/core/background.js): chrome.scripting.executeScript(world:'MAIN', files:['pageWorld.js'])
```

Build (`gulpfile.babel.ts`): webpack produces `packages/core/inboxsdk.js`
(loader + implementation), `packages/core/pageWorld.js` (from
`./src/injected-js/main`), plus REMOTE / NONREMOTE /
NONREMOTE-INTEGRATED-PAGEWORLD / TEST variants
(`src/inboxsdk-js/inboxsdk-*.ts`). `packages/core/background.js` is shipped to
consumers and does the MV3 MAIN-world injection.

## 4. What is worth reusing (ranked)

1. `SelectorRegistry` + overrides (parametrise by table).
2. `ElementWithLifetime` stream family + `kefir-stopper` lifetimes.
3. `Membrane` + `HandlerRegistry` + `SafeEventEmitter` triad (public-view
   identity and handler replay).
4. MV3 MAIN-world injection (`background.js` + `inject-script.ts`).
5. `xhr-proxy-factory` (+ tests) and the _pattern_ of network-derived identity
   with an AMBIGUOUS marker.
6. `censorHTMLtree` / `censorJSONTree` for fixture sanitising.
7. Build pipeline and `examples/` scaffolding.
8. Handwritten public `.d.ts` + `REQUESTED_API_VERSION` gating.

## 5. Lifecycle caveats specific to reuse

- `makeElementChildStream(parent)` observes **direct children only**. Gmail's
  rows live in a stable table; if Calendar re-parents chips across re-rendered
  column containers, direct-child observation will emit spurious destroy/create
  pairs. Prefer a single root observer that classifies added/removed subtrees
  (see plan §7) and keeps `WeakMap<Element, Driver>`.
- It reports inconsistent bookkeeping by `setTimeout(() => {throw})`. Fine for
  Gmail; for Calendar route those into the compatibility reporter, not the
  console.
- `HandlerRegistry.addTarget` mutates arrays with `remove()` + `indexOf`; O(n)
  per op. With hundreds of event views a `Set` is preferable (cheap change).
- Kefir is used everywhere internally; public API never exposes it (good). Keep
  Kefir internally for now; do not attempt a rewrite in Phase 1.

## 7. Trusted Types (checked later; not a constraint for content scripts)

Calendar serves `require-trusted-types-for 'script'`, which blocks `innerHTML`
and friends for page/MAIN-world code and in CDP-created isolated worlds — but
**a real MV3 content script is exempt** (RE log §1.18, verified with
`examples/calendar-smoke`). InboxSDK-style `innerHTML` widgets are therefore not
ruled out by it. Only a MAIN-world shim must avoid HTML-string sinks.
